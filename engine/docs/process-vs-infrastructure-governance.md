# 流程治理 vs 基础设施治理：本仓库的分工与落地

> **状态**：现行说明
> **定位**：说明本仓库两类治理的分工——**流程治理**定义「应该怎么做」，**基础设施治理**确保「必须做到」。二者目标一致、存在交叉。
> **配套**：[页面构建治理](./page-build-governance.md)、[报告全链路体系](./report-pipeline-system.md)、[多会话 Git 协议](./multi-session-git-protocol.md)。
> **最后更新**：2026-11-16

---

## 一、核心定义

| | 流程治理（Process Governance） | 基础设施治理（Infrastructure Governance） |
|---|---|---|
| 关注 | **How** — 如何思考、协作、决策 | **What** — 用什么工具、约束、自动化 |
| 作用对象 | 人的行为与协作方式 | 系统与技术约束 |
| 本质 | 社会性（文化、习惯、方法论） | 技术性（工具、自动化、策略） |
| 执行方式 | 引导、建议、规范 | 强制、校验、阻断 |
| 约束强度 | 软约束（可跳过） | 硬约束（不可绕过） |
| 可度量性 | 难度量 | 易度量（测试通过率、门禁退出码） |
| 变更频率 | 随项目阶段变化 | 相对稳定 |
| 失败表现 | 流程形同虚设、依赖自觉 | 规范无法执行、工具链失效 |
| 成熟标志 | 团队形成共识和习惯 | 工具链自动化、可观测 |

## 二、本仓库的落地对照

| 治理领域 | 流程侧（软，引导） | 基础设施侧（硬，阻断） |
|---|---|---|
| 需求 / 选型 | [六族十二类](./report-classification.md) 选型参考、类型模板 | 类型引用必须已在 `template-registry.md` 注册（G0 `[E]`） |
| 目录 / 命名 | 按主题声明的维度顺序（`AGENTS.md` + `engine/tools/layout.json`） | `validate_layout.py` 对维度序列与主题声明不符判 `[E]` |
| 页面构建 | [PAGE-BUILD-SPEC](./page-build-spec.md) 规范正文 | `page_build_check.py` P01–P15，`[E]` 阻断合并 |
| 内容质量 | [信息分层](../templates/information-layering-spec.md) / [决策交付](../templates/decision-delivery-spec.md) | 四门禁 + 研究内核纳入统一门禁 |
| 来源 / 数据 | 来源四级分层、双源确认、采集 SOP | `source_check.py` R1–R7 + 死链探测 |
| 报告审计 | [审计四环节](../audit/review-workflow.md)、L3 语义由 Agent 写证据 | `audit_tool.py run --strict` fail-fast + 标识三态 |
| 提交 / 合并 | [多会话 Git 协议](./multi-session-git-protocol.md) | `repo_sync.py run --gate` + pre-push refspec 守卫 + main 分支保护 |
| 运维 / 告警 | 维护任务清单、定期复盘 | CI 五工作流 + `webhook-alert.yml` + 闭环修正工单 |
| 效率 | 分层监测、增量复核 | `perf_monitor.py` P95 阈值 |

## 三、生命周期作用点

```
需求 → 设计 → 开发 → 审查 → 合并 → 发布 → 监控
  └────── 流程治理（贯穿全程，作用于每个阶段）──────┘
        ↑       ↑      ↑      ↑      ↑      ↑
     提交前   PR    合并   审计   发布   告警
         基础设施治理（作用于检查点，强制校验）
```

---

## 四、依赖关系

```
流程治理定义「应该做什么」
         ↓
基础设施治理确保「必须做到」
         ↓
两者共同保障「交付质量」
```

- **没有流程治理的基础设施**：有 CI 但不知道该检查什么；有分支保护但不知道分支按什么策略管理；有扫描但不知道标准从哪来。
- **没有基础设施治理的流程**：有 spec 但没有东西确保它被遵循；有 review 流程但没有东西确保 review 发生；有规范但没有东西确保规范被执行。
- **对 AI 驱动开发的意义**：Agent 可能「忘记」调用规范或「假装」完成——流程治理依赖主动性；CI、门禁、钩子、分支保护不依赖 Agent 的自觉，是唯一可靠的兜底。

## 五、实践建议

**最小可行硬约束**（已在本仓库落地）：

1. **统一门禁**：`optimization_gate.py` 21 项单一入口，`[E]` 阻断合并 / 提交。
2. **分支保护**：禁止直推 `main`；PR + 必需检查 + strict。
3. **基础 CI**：语法 → 单测 → 统一门禁，全绿方可合并。
4. **提交网关**：`repo_sync.py run --gate`，提交前复用统一门禁。
5. **审计兜底**：`audit.yml` fail-fast + 闭环修正工单。

**配合分工**：

| 可以「交给」流程治理的 | 仍需基础设施兜底的 |
|---|---|
| 选型、模板复用、业务配置撰写 | 门禁口径、类型注册校验 |
| 审计语义判定、L3 证据 | 审计留痕、标识注入、fail-fast |
| 监测分层、增量复核策略 | 性能阈值、告警链路 |
| 多会话协作约定 | 检出锁、rebase、pre-push 守卫 |

**一句话**：流程治理是「地图」，基础设施治理是「护栏」——地图告诉你该往哪走，护栏确保你不会掉下悬崖。
